# FeedForward — Database Design

ERD and business rules for the MySQL schema, as designed step by step for the main workflow (donor lists surplus → tiered → recipient claims → pickup logged).

## Business Rules

**Organization hierarchy**
1. `Donor` and `Recipient` are subclasses of `Organization` (table-per-subclass / class-table-inheritance): each one's primary key *is* the foreign key back to `Organization.org_id` — no separate surrogate ID — enforcing a strict 1-to-1 "is-a" relationship.
2. `Recipient.type` must be one of `'pantry'`, `'farm'`, `'compost'`.

**Items**
3. `Item.tier` must be one of `1` (people), `2` (animal feed), `3` (compost).
4. `Item.total_weight` is a generated column (`quantity * unit_weight`), never written directly — guarantees it can never drift out of sync.
5. `Item.category_id` references the `Category` lookup table rather than a hardcoded enum, so new categories can be added via `INSERT` without a schema change.

**Recipient acceptance rules (all normalized to satisfy 3NF — no multivalued attributes in one row)**
6. Accepted tiers live in `AcceptedTier`, one row per `(recipient_id, tier)`.
7. Refused categories live in `RefusedCategory`, referencing `Category` — refusing a category (e.g. "cookies") implicitly refuses every item under it (e.g. "Oreos Double Stuff Kroger").
8. Pickup windows live in `AcceptanceRule`, one row per window: `day_of_week` reflects the day `pickup_start` falls on. `pickup_end` may be less than, greater than, or equal to `pickup_start` (supports overnight wraps and 24-hour/all-day windows). `UNIQUE(recipient_id, day_of_week, pickup_start)` blocks exact duplicate windows while still allowing multiple distinct windows per day.

**Claims and pickups**
9. A `Claim` represents a recipient reserving an `Item` before collection (`claim_time`, intended `pickup_time`).
10. `Pickup` is the completed event and stays minimal — it references only `claim_id`; donor/recipient/item are derived by joining through `Claim` rather than duplicated.
11. A `BEFORE INSERT` trigger on `Pickup` resolves the item through its `Claim`, rejects the insert (via `SIGNAL`) if the pickup's `quantity` exceeds the item's current `quantity`, and otherwise decrements `Item.quantity` by that amount — enforced this way because MySQL `CHECK` constraints cannot query another table.

**Other**
12. Impact-dashboard metrics (total lbs, lbs by tier, meals, pickup history) are **not** a stored entity — computed on demand via aggregate queries over `Pickup` → `Claim` → `Item` → `Organization`.
13. Zip codes and phone numbers are stored as fixed-format strings (`CHAR(5)` / `VARCHAR(20)`), not numeric types, to preserve leading zeros and formatting.
14. Timestamp-on-insert columns (e.g. `date_registered`) use `DEFAULT CURRENT_TIMESTAMP`, not a generated column — MySQL generated columns must be deterministic and can't call `NOW()`.
